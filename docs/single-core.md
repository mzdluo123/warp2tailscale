# 单核出口的系统调用和队列

2026-11-21（新加坡时间）。s2 服务所有线程固定到一个逻辑 CPU，Go 并行度为 1，使用 x86-64-v4 构建。内层 BBR 的突发上限为 24 MSS、1 ms，单流速率由 BBR 估算。独立 Linux 客户端直连出口，禁用应用代理、取消限速。下载使用固定 CDN 地址的 15 MiB HTTPS Range，上传向受控 HTTPS 接收端发送测试数据并核对响应。全程使用自然链路。

## UDP 系统调用

Linux syscall tracepoint 按服务 PID 和 UDP socket 统计进入及返回。调用次数包括返回 EAGAIN 的非阻塞接收。每次成功调用的 UDP 数据报数按返回的消息数量、每条消息的实际字节数以及 UDP GSO/GRO 控制消息计算。分母为客户端交付的下载正文或服务器确认的上传正文。两轮区间如下，上传每轮 4 条连接各交付 8 MiB，下载每轮预热 7 秒后取约 8 秒。计数覆盖服务的全部流量。带探针的吞吐与无探针测试分开记录。

| 应用方向 | s2 套接字与调用 | 调用次数/MiB | 数据报/成功调用 |
|---|---|---:|---:|
| 下载，16 流 | WARP sendmsg | 796–802 | 1.00 |
| | WARP recvmmsg | 226–229 | 6.91–6.98 |
| | WireGuard sendmmsg | 450–495 | 1.88–2.04 |
| | WireGuard recvmmsg | 240–249 | 1.86–1.87 |
| 下载，24 流 | WARP sendmsg | 836–884 | 1.00 |
| | WARP recvmmsg | 241–248 | 6.99–7.13 |
| | WireGuard sendmmsg | 501–585 | 1.59–1.86 |
| | WireGuard recvmmsg | 256–265 | 1.87–1.89 |
| 上传，4 流 | WARP sendmsg | 1476–1492 | 1.00 |
| | WARP recvmmsg | 707–745 | 1.80–1.86 |
| | WireGuard sendmmsg | 520–547 | 1.00 |
| | WireGuard recvmmsg | 1188–1211 | 1.30–1.33 |

WireGuard 发送端实测使用 UDP GSO，包括一次由 9 个 1296 字节报文组成的提交。虚拟网卡的硬件 UDP 分段为 `off [fixed]`，Linux 可以软件分段。WARP 的 QUIC 套接字也使用了 UDP_SEGMENT 控制消息，但以上上传和下载窗口里每次发送均只有一个实际数据报。关闭 `runtime.udp_gso` 后，两个套接字的发送跟踪均未出现 UDP_SEGMENT。后续的 `sendmmsg` 试验保留每条消息独立的长度、目的地址和控制消息。[quic-go GSO 说明](https://quic-go.net/docs/quic/optimizations/) · [Linux sendmmsg](https://man7.org/linux/man-pages/man2/sendmmsg.2.html)

## 16 与 24 并发的额外工作

| 每交付 1 MiB | 16 流，两轮 | 24 流，两轮 |
|---|---:|---:|
| 带采样的服务 CPU 时间（ms） | 37.76、37.95 | 45.65、38.84 |
| 客户端侧 gVisor 收到的 TCP ACK | 358、380 | 416、391 |
| BBR pacing 定时器回调 | 280、292 | 374、307 |
| 客户端侧重传，折算 MSS | 0.033、5.916 | 0.218、0.232 |
| WARP 侧本机 TCP 发送重传，折算 MSS | 0、0 | 0、0.010 |
| HTTP/3 流接收队列满而丢弃的数据报 | 276、297 | 352、332 |
| 三个外层 UDP 套接字的接收丢包增量 | 0、0 | 0、0 |

ACK 按内层发送端逐流计数。四个约 8 秒窗口中，活跃连接的 ACK 数中位数按表内顺序分别为 4798、2576、1540、2487。连接在窗口内可能建立或关闭；单流中位数同时受存活时间影响。内层重传随并发数没有一致增长。24 流两轮的 ACK、pacing 唤醒及 HTTP/3 队列丢弃次数都高于 16 流。WARP 侧本机发送计数只观测本机发出的 TCP 重传，远端 CDN 对已丢下载数据的重发不在此计数内。

在 HTTP/3 流的接收者从空队列唤醒时，检查当时已就绪的 CONNECT-IP 数据报。以携带数据的 TCP 段为队首，16 流两轮平均有 21.3–22.1 个包就绪，队首同流连续序号的 TCP 段平均约 6 个。24 流平均有 22.0–24.0 个包就绪，连续段平均约 5 个。连续序号只表示候选，GRO 还需验证协议头、标志、长度和校验和。上传窗口的队首以 ACK 为主，携带数据的 TCP 段样本仅 27 和 41 次。

## 发送批处理与 WARP 接收 GRO 试验

发送试验先用原路径立即发送队首，再读取已就绪的队列长度；至少有两条后续消息时调用 Linux `sendmmsg`。不同长度的数据报各自保留 ECN 和 GSO 控制消息。一次只检查调用行为的采样中，WARP 套接字的 13,681 次 `sendmmsg` 成功提交了 92,083 个数据报，平均每次 6.73 个，最大 8 个。该次采样期间发生了换路，其下载速率不用于比较。

接收试验每次从 CONNECT-IP 读取最多 8 个已就绪的数据报，在注入 WARP 的 gVisor 栈前做 TCP GRO，批末立即 flush。发送、接收可以在同一试验进程内独立切换，服务 PID 和套接字保持不变。下表列出同一个客户端 IPv4 直连端点上，HTTP 完整、往返采样充足、窗口内无丢失的试验轮次。四种模式都保留原有 UDP GSO。

| WARP 试验模式 | 并发 | 吞吐 MB/s | CPU ms/MiB | 节点空闲 RTT P50 | 节点负载 RTT P95 | 公网负载 RTT P95 |
|---|---:|---:|---:|---:|---:|---:|
| 发送批处理 | 16 | 29.65 | 33.45 | 214 ms | 217 ms | 227 ms |
| 接收 GRO | 16 | 33.26 | 29.53 | 214 ms | 259 ms | 300 ms |
| 发送批处理和接收 GRO | 16 | 37.79 | 26.16 | 214 ms | 337 ms | 355 ms |
| 发送批处理和接收 GRO | 24 | 37.56 | 26.84 | 214 ms | 279 ms | 312 ms |
| 接收 GRO | 24 | 35.46 | 28.25 | 214 ms | 346 ms | 279 ms |
| 发送批处理，重复 | 16 | 25.83 | 37.94 | 214 ms | 219 ms | 222 ms |

同进程交叉测试共 16 轮。其余 10 轮出现了端点切换、请求失败或 ping 丢失，包含该组全部基线轮次。连续几轮只有 0.23–0.37 MB/s，基线和三种试验模式都受影响。服务仍在线；样本不足以确定这段异常的原因。另一组独立重启测试中，基线两次 16 并发达到 29.19 和 30.87 MB/s，CPU 分别为 34.63 和 32.41 ms/MiB，负载 RTT P95 比各自空闲中位数高 9 和 2 ms。这两轮使用不同的公网路径。

发送批处理降低了系统调用次数，在完整链路上每 MiB 的 CPU 收益仍有波动。接收 GRO 能提高单核吞吐，同时测到了显著的负载延迟。生产配置保留 WireGuard 和 WARP 原有的 UDP GSO，WARP 的额外发送批处理与接收 GRO 仅用于此次试验。

## 单独验证 WireGuard GSO

在 s2 的独立网络命名空间内，让两个加密 tsnet 端点共用同一个逻辑 CPU。每轮传输 512 MiB，同时通过另一条 TCP 连接测小请求的 RTT，计时前后都确认 UDP 直连。以关、开、开、关、关、开的顺序切换两端 WireGuard 发送 GSO。下表为各三轮中位数，CPU 时间包含发送端和接收端。

| WireGuard GSO | 吞吐 MB/s | CPU ms/MiB | 负载 TCP echo RTT P95 |
|---|---:|---:|---:|
| 关闭 | 100.75 | 10.377 | 27.94 ms |
| 开启 | 265.17 | 3.887 | 3.44 ms |

该组隔离测量涵盖 WireGuard 和两端用户态 TCP 栈。真实客户端到公网同时经过跨网链路、WARP 及 CDN，其吞吐需使用前面的端到端测试衡量。

## 恢复生产配置后的公网验收

s2 全部服务线程固定在 CPU 1。生产版本使用软件 UDP GSO、内层 BBR、8 MiB 发送与 4 MiB 接收缓冲区，逐流日志关闭。两轮直连端点一致，客户端应用均无代理、无限速，所有已完成的下载均返回预期的 HTTP 206 与正文长度。

| 并发 | 吞吐 MB/s | 服务单核 CPU | CPU ms/MiB | 到 s2 空闲 P50 / 负载 P95 | 到公网空闲 P50 / 负载 P95 |
|---:|---:|---:|---:|---:|---:|
| 1 | 16.05 | 56.4% | 36.81 | 176 / 177 ms | 178 / 185 ms |
| 16 | 29.50 | 97.2% | 34.55 | 176 / 177 ms | 178 / 185 ms |

独立客户端的默认域名解析、IPv4/IPv6 HTTPS、显式 UDP/53、HTTP/3 与公网 ICMP echo 均通过，双栈 Cloudflare trace 均返回 `warp=on`。最终核对 systemd 服务为 active、enabled，节点已通告出口路由且 MASQUE 已连接。

## QUIC 接收复制与 HTTP/3 环形队列

同一 s2 单核出口、独立 Linux 客户端直连、应用无代理、无限速。QUIC 接收队列可以接管解析器已从解密缓冲区复制出来的 DATAGRAM；下一次读包可以立即复用原始缓冲区。另一个改动用环形队列保存 HTTP/3 流的待收数据报。HTTP/3 流队列的两种实现都按 FIFO 交付，容量为 32，满时丢弃新到的包，不增加定时等待。

**s2 本机微基准。** 原版与改动版在同一个逻辑 CPU 上各测三轮，下表为中位数。第一项解析 1200 字节载荷并完成入队和出队；第二项保持队列半满，反复入队和出队，测量队列本身。

| 操作 | 原版 ns/op | 改动后 ns/op | 原版 → 改动后分配 |
|---|---:|---:|---|
| 解析、入队、出队 | 354.0 | 210.9 | 2616 → 1336 B/op，4 → 3 次/op |
| HTTP/3 队列入队、出队 | 28.33 | 16.24 | 42 → 0 B/op |

**公网交叉测试。** 在同一试验进程内单独切换这两项改动，原有 UDP GSO、BBR 和 1 ms 突发窗口照常使用。每组先预热 7 秒，再统计约 8 秒内客户端收到的 HTTPS 正文、服务 CPU、HTTP/3 队列满丢弃和 RTT。按相反顺序复测，每格为两轮中位数。16 轮起止均为同一客户端侧 IPv6 直连端点，所有已完成的请求均为预期的 HTTP 206。

|---:|---|---:|---:|---:|---|
| 16 | 基线 | 24.93 | 38.97 | 288.35 | +1、+68 |
| 16 | 仅去掉复制 | 26.75 | 36.89 | 277.96 | +2、+1 |

| 24 | 基线 | 24.78 | 40.23 | 276.12 | +1、+2 |

上传交叉测试共四轮，每轮 4 条连接各 POST 8 MiB，接收端完整确认 128 MiB。基线两轮均为 3.49 MB/s；两项同开为 3.43 和 3.76 MB/s。s2 生产采用去重复制，YAML 中 `warp.http3_receive_ring: false`。需要复查环形队列时可改为 `true` 并重启。

## 减少数据路径上的暂存拷贝

- Tailscale 将 gVisor 发来的各段直接写入 WireGuard 发送缓冲，不先展平成临时切片。WARP 路由返回的 UDP/ICMP 包也移交一个包引用，在同一位置复制；读取或关闭队列时释放引用。
- gVisor 在进入入站过滤前释放校验视图；IPv6 无扩展头的 TCP、UDP 和 ICMPv6 本地交付不再构建扩展头迭代器。保留防火墙执行后的包头读取及传输层交付所需的所有权隔离。
- MASQUE 直接交付 CONNECT-IP 接收载荷，不复制到 MTU 暂存缓冲。发送时将 CONNECT-IP 和 HTTP/3 前缀及载荷一次写入 QUIC 队列自有缓冲；保留包长检查、MTU 截断和加密缓冲。

本地 Linux（WSL2，Core Ultra 7 270K Plus，Go 1.27.3）固定在同一逻辑 CPU 上交替运行对照。发包和 MASQUE 各 5 轮，IP 接收各 3 轮，取中位数。MASQUE 基准对照重建旧的两级暂存，只计帧组装和入队，不计加密、网络或对端处理。

| 片段 | 耗时 ns/op，前 → 后 | 堆分配 B/op，前 → 后 |
|---|---:|---:|
| Tailscale 发送，1200 字节 TCP 载荷 | 263.8 → 66.1 | 1280 → 0 |
| Tailscale 发送，8 段 TCP GSO | 1540 → 411 | 9728 → 0 |
| gVisor IPv4 UDP 接收 | 571.6 → 541.9 | 0 → 0 |
| gVisor IPv6 UDP 接收 | 812.6 → 553.6 | 160 → 80 |
| MASQUE DATAGRAM 组装和入队，1280 字节 | 434.4 → 162.4 | 4256 → 1440 |
